
# 高中数学知识库系统技术设计文档

**版本：V1.2（最新整合版）**  
**更新日期：2026-11-05**  
**系统定位：面向教师教学 Agent 的高中数学专业知识库**

---

# 一、项目概述

## 1.1 建设目标

建设一个面向高中数学教师教学场景的专业知识库，为教师教学 Agent 提供可靠、可追溯、可检索的数学知识和题目数据。

知识库不仅是 PDF 文件存储系统，也不仅是向量数据库，而是将教材、历年高考真题和模拟题加工成具有明确结构、数学语义、来源信息和关联关系的数据系统。

最终支持教师教学 Agent 完成：

1. 根据知识点、章节、题型、难度和考试年份检索内容。
2. 查询教材中的定义、定理、公式、性质和例题。
3. 检索完整试题、单个小题、答案、解析以及相关图形。
4. 将题目与教材知识点、解题方法、公式建立关联。
5. 为教师提供备课、讲题、变式训练、试卷分析和教学设计支持。
6. 回答时引用原始资料、页码、题号和内容片段。

## 1.2 第一版数据范围

V1 纳入以下全部数据：

| 数据类别 | 具体内容 |
|---|---|
| 高中数学教材 | 必修、选择性必修教材 |
| 高考真题 | 历年全国卷及纳入范围的地方高考数学真题 |
| 高考模拟题 | 各地区、学校及机构的高质量模拟试卷 |
| 答案与解析 | 参考答案、标准解析、评分说明 |
| 数学图像 | 函数图像、几何图形、统计图表、题目配图 |

支持的数据格式：

- PDF
- 扫描 PDF
- JPG / PNG
- Markdown
- JSON

## 1.3 V1 基本原则

1. 原始 PDF 永久保留，不允许 OCR 结果覆盖原始文件。
2. 结构化数据是知识库的核心。
3. Markdown 负责阅读和维护，JSON 负责数据交换，数据库负责查询。
4. 检索不能只依赖向量相似度。
5. OCR 识别结果必须经过质量检测。
6. 重要公式、题目边界和图形关系支持人工审校。
7. 所有知识内容都必须能够追溯到原始资料。

## 2.1 架构原则

1. 原始文件不可覆盖。
2. 结构化数据为核心。
3. 检索不依赖单一技术。
4. 模型通过接口隔离，允许后续替换。
5. 低置信度数据进入人工复核。
6. 所有内容支持来源追溯。

# 三、模型选型与职责

## 3.1 V1 已确定的模型方案

| 模块 | 模型或方案 | 部署方式 | 主要职责 |
|---|---|---|---|
| 推理模型 | DeepSeek | 云端 API | Agent 推理、教学分析 |
| Embedding | Qwen3-Embedding-0.6B | 优先本地 CPU | 文本向量化 |
| Reranker | Qwen3-Reranker-0.6B | 优先本地 CPU | 检索结果精排 |
| OCR | Hybrid OCR | 本地与云端可切换 | 文本及版面识别 |
| 公式 OCR | UniMERNet 等候选 | 本地或云端 | 数学公式识别 |
| VLM | Qwen-VL（可选） | 本地或云端 | 页面视觉理解 |

## 3.2 DeepSeek 推理模型

主要负责：

- 理解教师的自然语言请求。
- 判断需要检索什么内容。
- 选择适当的检索工具。
- 分析检索结果。
- 组织教学内容。
- 生成讲解和备课材料。

DeepSeek 不负责替代 OCR，也不应在没有证据的情况下凭空还原原题。

## 3.3 Qwen3-Embedding-0.6B

负责将知识片段和用户查询转换为向量。

主要用途：

- 教材知识点语义检索。
- 数学题目相似度检索。
- 例题与知识点关联。
- 解题方法检索。
- 教材内容召回。

Embedding 只负责检索的一部分，不能单独承担公式精确匹配和题号检索。

## 3.4 Qwen3-Reranker-0.6B

负责对初步召回的候选内容进行相关性评分。

工作流程：

```text
用户查询
   ↓
Embedding 向量检索
   ↓
获取候选内容
   ↓
Reranker 精排
   ↓
返回高相关结果
```

Embedding 负责召回，Reranker 负责精排，两者不能相互替代。

## 3.5 Hybrid OCR

高中数学试卷包含：

- 普通文本。
- 数学公式。
- 几何图形。
- 函数图像。
- 表格。
- 双栏排版。
- 跨页题目。

单一 OCR 服务很难同时做好这些任务，因此采用多阶段组合处理。

## 3.6 Qwen-VL

作为可选视觉辅助模块。

主要用途：

- 几何图形辅助理解。
- 函数图像特征识别。
- 复杂页面视觉分析。
- 表格和图形布局理解。

不需要所有页面都调用 VLM。

## 3.7 本地硬件与部署策略

当前硬件：

- CPU：Intel Core Ultra 5 125H
- 内存：32 GB
- 独立显卡：无

部署策略：

1. 优先使用 CPU 部署 Embedding 和 Reranker。
2. 使用批量推理降低处理开销。
3. 对已处理内容缓存向量。
4. 控制 Reranker 的候选数量。
5. OCR 和 VLM 根据实际性能选择本地或云端。
6. DeepSeek 推理通过 API 调用。

需要实际测试模型的：

- 内存占用。
- 推理速度。
- 批量处理能力。
- CPU 利用率。
- 单条数据处理耗时。

不能仅根据模型参数量推断实际运行性能。

## 3.8 是否还需要其他模型

V1 暂时不需要增加独立的分类大模型或知识图谱模型。

题目分类、知识点标注和题目切分优先采用：

- 规则解析。
- 结构化数据。
- DeepSeek 辅助分析。
- 人工复核。

只有出现明确的质量瓶颈时才考虑增加模型。

# 四、Obsidian 知识管理方案

## 4.1 Obsidian 的定位

**Obsidian 是知识内容的人工阅读、审校、组织和维护工作区，不是系统的核心数据库，也不是向量检索引擎。**

使用 Obsidian 的原因：

1. 原生使用 Markdown。
2. 支持 YAML Frontmatter。
3. 支持双向链接。
4. 方便人工审校 OCR 结果。
5. 可以使用 Git 进行版本管理。
6. 适合长期维护知识内容。

## 4.3 Obsidian 与后端的数据关系

推荐采用以下流程：

```text
OCR 和解析服务
       ↓
生成标准 JSON
       ↓
生成 Markdown + YAML
       ↓
Obsidian 人工审校
       ↓
同步程序读取审校后的文件
       ↓
更新 PostgreSQL
       ↓
更新 Embedding 和 Qdrant
```

注意：

- 不让 Obsidian 插件承担复杂的数据导入任务。
- 不把 Obsidian 内部链接当作数据库外键。
- Markdown 与 JSON 必须使用统一字段规范。
- 人工修改必须保留版本信息。
- 重新 OCR 时不能覆盖人工修订内容。

# 五、Hybrid OCR 系统设计

## 5.1 OCR 总体流程

```text
PDF 导入
   ↓
文件指纹计算与去重
   ↓
文件类型识别
   ↓
PDF 页面拆分
   ↓
页面分类
   │
   ├── 数字原生 PDF
   │       ↓
   │   PDF 原生文本提取
   │
   └── 扫描 PDF
           ↓
       图像预处理
           ↓
          OCR
   │
   ↓
版面分析
   ↓
公式、表格、图形专项处理
   ↓
题目与小题切分
   ↓
答案、解析关联
   ↓
生成结构化 JSON
   ↓
质量检测
   ↓
人工复核
   ↓
生成 Markdown
   ↓
进入知识库
```

## 5.2 页面类型判断

| 页面类型 | 处理策略 |
|---|---|
| 数字原生 PDF | 优先提取 PDF 原生文本 |
| 扫描文本页 | OCR 识别 |
| 公式密集页 | 普通 OCR + 数学公式识别 |
| 几何图形页 | 图像裁剪保存 + 视觉辅助分析 |
| 表格统计页 | 表格结构识别 |
| 混合页面 | 分区域处理后恢复阅读顺序 |

不应对所有页面无差别调用同一种 OCR。

## 5.3 普通文本识别

主要任务：

- 识别中文题干。
- 识别英文字符。
- 识别数字和数学符号。
- 恢复段落结构。
- 保留文本块坐标。
- 保留页码和阅读顺序。

优先提取 PDF 原生文本，只有无法提取或质量不足时才使用 OCR。

## 5.4 数学公式识别

公式识别必须独立处理。

流程：

```text
页面图像
   ↓
公式区域检测
   ↓
公式图像裁剪
   ↓
数学公式 OCR
   ↓
LaTeX 输出
   ↓
公式语法检查
   ↓
人工复核
```

重点关注：

- 分数。
- 根式。
- 上下标。
- 积分。
- 求和符号。
- 极限。
- 矩阵。
- 向量。
- 分段函数。
- 多行公式。

需要同时保存：

1. LaTeX 字符串。
2. 原始公式图片。
3. 公式所在页码。
4. 页面坐标。
5. 识别模型和版本。
6. 识别置信度。
7. 人工校验状态。

不能只保存 OCR 生成的普通文本。

## 5.5 几何图形和函数图像

对于数学图形：

- 保存原始图形。
- 保存图形所在页面。
- 保存图形坐标。
- 保存关联题目 ID。
- 保存必要的视觉描述。

例如：

```json
{
  "figure_id": "fig_001",
  "question_id": "q_001",
  "figure_type": "geometry",
  "image_path": "09_Assets/fig_001.png",
  "source_page": 3,
  "bbox": [100, 200, 500, 600],
  "description": "包含三角形 ABC 的几何图形",
  "description_status": "machine_generated"
}
```

注意：视觉模型生成的图形描述不能直接作为严格数学条件，必须经过核验。

## 5.6 题目切分

题目切分结合以下信息：

1. 题号。
2. 小题编号。
3. 选择题选项。
4. 题目关键词。
5. 段落结构。
6. 页面坐标。
7. 试卷结构模板。
8. 答案解析中的题号。

采用：

**规则优先 + 模型辅助 + 结构校验 + 人工复核。**

不能完全依赖正则表达式，也不能完全依赖大模型。

## 5.7 OCR 质量状态

统一采用：

| 状态 | 含义 |
|---|---|
| pending | 待处理 |
| processing | 处理中 |
| machine_checked | 机器检查通过 |
| needs_review | 需要人工复核 |
| human_verified | 人工确认 |
| failed | 处理失败 |

重点检查：

- 题号是否连续。
- 题干是否缺失。
- 公式是否错误。
- 选项是否正确关联。
- 答案是否对应正确题目。
- 图形是否关联正确。
- 跨页题目是否完整。

# 七、数学知识组织

## 7.1 知识点体系

以高中数学教材体系为主线建立知识点树。

```text
高中数学
│
├── 预备知识
│
├── 集合与常用逻辑用语
│
├── 函数
│   ├── 函数概念与性质
│   ├── 基本初等函数
│   └── 函数应用
│
├── 三角函数
│
├── 平面向量
│
├── 复数
│
├── 立体几何
│
├── 统计与概率
│
├── 数列
│
├── 导数
│
└── 解析几何
```

具体层级需要根据实际采用的教材版本和课程标准确定。

## 7.2 题目标签体系

题目需要分别管理以下标签：

| 标签类型 | 说明 |
|---|---|
| 知识点 | 题目考查的数学知识 |
| 题型 | 选择题、填空题、解答题 |
| 方法 | 数形结合、换元、构造、分类讨论等 |
| 能力要求 | 运算、推理、建模等 |
| 难度 | 简单、中等、困难等 |
| 来源属性 | 年份、地区、试卷类型 |

## 7.3 知识关联

建立以下关系：

- 题目 → 知识点
- 题目 → 解题方法
- 题目 → 教材章节
- 题目 → 相似题
- 知识点 → 前置知识点
- 知识点 → 定理和公式
- 教材例题 → 对应练习题

V1 使用 PostgreSQL 关系表和稳定 ID 管理关系，暂不引入独立图数据库。

# 八、数据存储设计

## 8.1 原始文件存储

保存：

- 原始 PDF。
- 原始图片。
- 页面截图。
- 公式裁剪图。
- 几何图形裁剪图。

原始文件只读保存，使用文件哈希实现去重。

## 8.2 PostgreSQL

作为结构化数据和业务元数据的主要数据库。

存储：

- 文档信息。
- 页面信息。
- 题目。
- 小题。
- 选项。
- 答案。
- 解析。
- 知识点。
- 解题方法。
- 题目关联关系。
- OCR 状态。
- 人工审校记录。

## 8.3 Qdrant

作为向量数据库。

存储：

- 向量 ID。
- 对应实体 ID。
- Embedding 向量。
- 必要的过滤元数据。

注意：Qdrant 不作为唯一事实来源。题目正文、答案、解析和来源等权威数据仍以 PostgreSQL 和标准化文件为准。

## 8.4 Markdown / YAML

用于 Obsidian 阅读、编辑、审校和知识组织。

通过同步程序与 PostgreSQL 保持一致。

## 8.5 数据一致性

每个可索引内容块需要：

- 稳定 ID。
- 内容哈希。
- 版本号。
- 更新时间。

内容发生变化时：

1. 检查内容哈希。
2. 判断是否需要重新切分。
3. 判断是否需要重新计算 Embedding。
4. 更新 PostgreSQL。
5. 更新 Qdrant。
6. 记录同步状态。

# 九、切分与索引策略

## 9.1 不采用单一固定长度切分

数学知识内容具有明显结构，不能简单地每 500 或 1000 个字符切成一块。

采用结构化切分：

| 内容类型 | 推荐切分单位 |
|---|---|
| 教材正文 | 标题、自然段、知识点 |
| 定义和定理 | 独立知识单元 |
| 公式 | 公式及其解释上下文 |
| 例题 | 完整例题 |
| 试卷题目 | 完整题目或独立小题 |
| 解析 | 对应题目的完整解析或步骤 |
| 图形 | 关联题目资源 |

## 9.2 多粒度索引

同一份资料可以建立多个检索粒度：

1. 文档级。
2. 章节级。
3. 知识点级。
4. 题目级。
5. 小题级。
6. 解析级。

必须保留父子 ID。

例如，检索到某个小题时，可以进一步获取：

- 完整题目。
- 所属试卷。
- 参考答案。
- 完整解析。
- 相关图形。
- 对应知识点。

## 9.3 Embedding 输入设计

建议将必要的上下文与正文组合。

例如：

```text
资料类型：高考真题
年份：2024
试卷：新课标全国Ⅰ卷
题号：第1题
题型：单项选择题
知识点：函数
题目内容：……
```

不要把大量无关元数据拼入正文。

## 9.4 数学检索特殊处理

数学检索需要组合：

- 关键词检索。
- PostgreSQL 全文检索。
- 数学知识点过滤。
- 题型过滤。
- Embedding 向量检索。
- Reranker 精排。
- 公式标准化匹配。

对于公式精确匹配，应使用标准化 LaTeX 和结构化字段辅助检索，不能认为普通语义向量能够区分所有数学表达式。

# 十、混合检索系统

## 10.1 检索流程

```text
教师提出问题
      ↓
Agent 判断检索意图
      ↓
提取检索条件
      │
      ├── 知识点
      ├── 章节
      ├── 年份
      ├── 题型
      ├── 难度
      └── 地区
      ↓
并行检索
      │
      ├── PostgreSQL 全文/字段检索
      │
      └── Qdrant 向量检索
      ↓
合并候选结果
      ↓
去重
      ↓
Qwen3-Reranker 精排
      ↓
回溯父级题目和章节
      ↓
构造检索上下文
      ↓
DeepSeek 分析
      ↓
返回答案及来源
```

## 10.2 检索示例

教师提出：

> 找出近五年考查函数单调性、难度中等的高考题。

Agent 解析为：

```json
{
  "document_type": "gaokao",
  "year_range": [2022, 2026],
  "knowledge_points": ["函数单调性"],
  "difficulty": "medium",
  "question_type": null
}
```

随后执行：

1. PostgreSQL 结构化过滤。
2. 全文检索。
3. Qdrant 向量检索。
4. 合并结果。
5. Reranker 排序。
6. 返回题目及来源。

## 10.3 检索结果规范

必须尽可能返回：

- 题目正文。
- 来源文档。
- 年份。
- 地区。
- 试卷类型。
- 页码。
- 题号。
- 知识点。
- 答案。
- 解析。
- OCR 状态。
- 人工审校状态。

低可信 OCR 内容必须明确标记。

# 十一、教师教学 Agent

## 11.1 Agent 定位

知识库负责提供可靠内容和证据。

Agent 负责：

- 理解教师需求。
- 制定检索策略。
- 调用工具。
- 分析知识内容。
- 组织教学结果。

## 11.2 V1 功能

### 1. 数学知识问答

解释定义、定理、公式和数学概念。

### 2. 教材查询

根据教材版本和章节查找教学内容。

### 3. 题目检索

根据知识点、年份、题型和难度检索试题。

### 4. 题目讲解

基于题目、答案和解析生成教学讲解。

### 5. 备课辅助

围绕指定知识点组织教学内容。

### 6. 变式训练

基于已有题目分析变化维度，辅助生成新题。

### 7. 试卷分析

按知识点、题型和难度分析试卷结构。

## 11.3 Agent 工具接口

建议提供：

```text
search_documents
search_knowledge_points
search_questions
get_question
get_solution
get_textbook_section
get_related_questions
get_source_page
get_figure
```

所有工具尽可能返回结构化 JSON，而不是只有一段文本。

## 11.4 回答约束

1. 区分原始资料内容与模型生成内容。
2. 原题、答案和解析优先使用已审校数据。
3. 不确定的公式和答案必须说明不确定性。
4. 生成变式题时标注为模型生成。
5. 不得编造教材页码、年份和试卷来源。
6. 检索证据不足时明确说明。

# 十三、质量评估

## 13.1 OCR 评估

建立人工标注的测试数据集。

评估：

- 普通文本识别准确率。
- 数学公式识别准确率。
- 题目边界识别准确率。
- 小题关联准确率。
- 答案解析关联准确率。
- 图形关联准确率。
- 跨页题目恢复准确率。

数学公式不能只使用普通字符错误率评价，还必须检查数学语义是否发生变化。

## 13.2 检索评估

重点指标：

| 指标 | 含义 |
|---|---|
| Recall@K | 相关内容是否被召回 |
| MRR | 最相关结果的排名 |
| nDCG@K | 排序质量 |
| 过滤准确率 | 检索条件是否正确生效 |
| 来源完整率 | 来源信息是否完整 |
| 误召回率 | 不相关内容被返回的比例 |

## 13.3 Agent 评估

重点检查：

- 是否理解教师意图。
- 是否调用正确工具。
- 是否准确引用证据。
- 是否区分原始内容和生成内容。
- 是否避免编造。
- 数学讲解是否正确。

# 十八、最终设计原则

本系统的核心不是简单地把 PDF 导入向量数据库，而是建立完整、可靠的数据生产链：

```text
原始资料
   ↓
PDF 页面解析
   ↓
Hybrid OCR
   ↓
数学结构化
   ↓
人工审校
   ↓
Obsidian 知识维护
   ↓
PostgreSQL / Qdrant
   ↓
混合检索
   ↓
DeepSeek
   ↓
教师教学 Agent
```

各组件职责：

| 组件 | 核心职责 |
|---|---|
| Hybrid OCR | 将复杂数学资料转成结构化数据 |
| Obsidian | 知识阅读、组织和人工维护 |
| Markdown/YAML/JSON | 内容表达和数据交换 |
| PostgreSQL | 结构化事实和关系管理 |
| Qdrant | 语义向量召回 |
| Qwen3-Embedding | 文本向量化 |
| Qwen3-Reranker | 检索结果精排 |
| DeepSeek | 教学推理和内容组织 |

**V1 最重要的目标是保证数据正确、题目结构完整、公式可校验、来源可追溯、检索可评估。**

只有这些基础稳定后，才进一步扩大数据规模和 Agent 能力。
