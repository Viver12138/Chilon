# 真实教师验收 + 检索评估扩样本 · 设计方案（v0.1 草案）

> 目的：把“阶段 6 验收前夜”的两个空白补成可执行方案——
> ① 用真实教师和真实产品做场景 B/C/D（以及知识库检索）验收；
> ② 把检索评估从 15 条真人问题扩到有统计意义的样本，决定检索是否达标、Reranker 是否默认启用。
> 本文是设计稿，**不含执行结果**；执行前需确认样本与验收门槛。

## 0. 现状（为什么现在做）

- 产品侧：核心业务闭环（需求 → 方案审批 → 执行 → 发布 → 导出）、深 Seek 接入、SSE、知识库摄入/检索均已有实现与测试；**尚未做真实教师验收**。
- 设计走查侧：2026-11-04 只有 1 位教师跑过场景 A（线框图阶段）；D1 最核心的“编辑不重审 Plan”（场景 B）、G3 自动批准（场景 C）、知识库上传价值（场景 D）仍**未验证**。
- 检索侧：15 条真人问题（Q01–Q10、Q16–Q20，原文件缺 11–15），混合检索 Recall@8 **93.3%（14/15）**、MRR 0.836；但样本只有 15 条、判定为 lenient 片段匹配、无 strict target，**不是产品效果**。
- 知识库侧：教材 1797 块标注已 100% 教师复核并冻结（D.114–D.116），给验收提供了可用的教材/知识点底座；模拟题 734 条 model 标注仍未抽检，是验收时要如实说明的边界。

# 第一部分：真实教师验收

## A1. 验收对象与边界

| 项 | 定义 |
| --- | --- |
| 对象 | 当前可运行的产品（真实账号、真实平台语料、真实导出），**不是线框图** |
| 场景 | D2 §9 的 A/B/C/D 四张场景卡 + 新增 **E 知识库检索与引用**（直接验检索质量） |
| 不验 | 移动端、Admin/审核队列、教师私有资料（P1）、未上线的 deferred 页面 |
| 数据 | 平台语料 P0（教材 5 册/1797 块、高考真题、模拟题），**不收集学生数据** |
| 环境 | 独立实例 + 测试 Owner 账号；每场前数据库与导出目录重置；两场之间不串数据 |

## A2. 教师样本设计

目标 **4–6 位**真实高中数学教师，至少覆盖 2 个年级、3 个教龄段：

| 维度 | 分层 | 每层最少 |
| --- | --- | --- |
| 教龄 | <5 年 / 5–15 年 / >15 年 | 各 1 人（>15 年尤其重要：D3 已指出 3 年样本会高估流程容忍度） |
| 年级 | 高一/高二/高三 | 至少 2 个年级 |
| 系统经验 | 未用过 / 用过同类工具 | 未用过 ≥2 人 |
| 招募 | 同事/教研群/学校，**不选“技术爱好者”作为全部样本** | — |

记录（匿名）：`T01…`、教龄段、年级、是否用过 AI 工具、是否参与过设计走查、收集日期。不记录姓名/学校/联系方式到仓库。

## A3. 场景与任务脚本

每场 60–90 分钟，1 对 1 主持；教师边说边操作（think-aloud），主持人不提示操作路径，只在卡死 60 秒后给最小提示并记录“卡住”。

| 场景 | 任务（真实产品） | 验证假设 | 观察点/成功标准 |
| --- | --- | --- | --- |
| A 从零备一节课 | 三角图象与性质复习课：讲义 + 5 真题 + 2 模拟，导出学生版 | 文档定位、门禁可理解、导出信任 | 无协助完成整条链；能说清“批准的是什么”；学生版愿意发 |
| B 改已有讲义 | 上周讲义加“易错点”、换掉第 3 题，重新检查并发布 | **D1-03 编辑不重审 Plan**、G4/G5 接受度 | 知道“修改要新建草稿”；**知道不用重新批准计划**；能接受重跑检查；冲突提示位置合理 |
| C 10 分钟小测 | 正弦定理 5 道选择题、学生版、明天课上用 | **G3 自动批准**、小测是否也要检查、无答案确认 | 接受 auto 或明确说出“希望每次看一眼”；能否在 10 分钟内拿到文件；信任学生版 |
| D 纸质资料 | 手机拍照第 12 页两道题，上传、解析、审核、引用到讲义 | 知识库上传价值、OCR 错误可发现性 | 从拍照到可引用的时长；能否发现公式错误；是否觉得“手打更快”（最强负面信号） |
| E 检索与引用 | 用教师自己的 5 条检索需求找题/找概念，查看证据与出处 | 检索相关性、引用可追溯、证据不足处理 | 相关性 1–5 分；出处能否点回原文；无结果时系统是否说明“证据不足”而不是编造 |

说明：A–D 直接采用 D2 §9 现有脚本与必问问题；E 为本次新增，问题取自同一位教师真实需求（见 B 部分问题集），避免“为验收临时造题”。

## A4. 运行方式

1. **准备**：账号/语料/导出目录重置；准备场景卡（纸质）与同意书；录屏 + 录音（单独授权）。
2. **开场**：说明“测产品不是测你”，不评价对错；请教师按平时习惯操作。
3. **执行**：按 A→B→C→D→E 顺序（同一教师）；每场景结束做 3 分钟微访谈；全程观察员记录 D2 §9.7 表。
4. **收尾**：10 分钟半结构访谈（价值/信任/最想删掉的步骤/最担心的事）；5 题信任与负荷量表（1–7）。
5. **不干预原则**：卡住 60 秒才给最小提示；提示记入“卡点”；不替教师点按钮。
6. **数据留存**：录屏/笔记存本地受限目录（不进 git）；仓库只留匿名化报告与引语编号。

## A5. 验收指标与判定

### A5.1 每场景通过标准（建议）

| 场景 | 通过 | 有条件通过 | 不通过 |
| --- | --- | --- | --- |
| A | 无协助完成；门禁能说清；学生版愿意发 | 需 1–2 次提示但整体完成 | 卡死/不信任导出/明确说“不如自己写” |
| B | 知道新建草稿、知道不重审计划、接受重跑检查 | 知道但认为多余 | 认为“改稿还要重批”或找不到入口 |
| C | 接受 auto 或给出明确开关偏好；10 分钟内拿到文件 | 接受但要求每次看计划 | 不接受 auto 且无替代方案 |
| D | 拍照→引用完成；能发现公式错误；不认为手打更快 | 完成但嫌慢（记录时长） | 明确“手打更快”/不愿逐份确认 |
| E | 相关性中位数 ≥4；出处可追溯；无编造 | 相关性 3–4 或有 1 条无结果但解释清楚 | 相关性 ≤2 或出现编造来源 |

### A5.2 总体门槛

- **任务完成率**：A–D 每场景 ≥75% 教师无协助完成（4 人中 ≥3）；
- **阻断级信任失败**：0 例“不敢用/必须自己重做”；
- **关键假设**：D1-03（B）与 G3（C）各有 ≥3/4 教师给出同向结论，否则回到设计评审；
- **效率**：A 场景从提交到导出 P50 ≤ 20 分钟（与 M7 一致）；C ≤ 10 分钟；
- **检索**：E 场景 5 条检索的教师相关性评分中位数 ≥4/5，出处可追溯率 100%。

### A5.3 证据分级与处置

按 D2 §9.6 把每条反馈分为 **认知/效率/信任** 三类，分别只改文案/步骤/证据，不允许“用更多确认弹窗解决信任问题”。每条问题标 P0（阻断）/P1（影响使用）/P2（体验），进入 OPEN_ITEMS。

## A6. 产物与文档

- 匿名化验收报告：`docs/teacher_acceptance_2026-11-XX.md`（样本、逐场景结果、引语、指标、失败项、决策）；
- 观察原始表（本地受限，不入库）：D2 §9.7 记录表 + 量表；
- 设计改动清单：D3/D4/D5 的变更点 + D6 验收矩阵更新；
- 决策记录：通过/有条件通过/不通过 + 风险接受人。

## A7. 风险与伦理

| 风险 | 缓解 |
| --- | --- |
| 样本偏差（年轻/技术友好） | 分层招募；>15 年教龄至少 1 人；不全部来自同一学校 |
| 主持人不自觉提示 | 固定脚本 + 60 秒规则 + 观察员独立记录 |
| 隐私/合规 | 不收集学生数据；录屏单独授权；仓库只存匿名引语 |
| 教师时间成本 | 60–90 分钟/人，提供教研参与证明或课酬（按学校规定） |
| 一次验收就下结论 | 关键假设要求 ≥3/4 同向；与检索数据交叉验证 |

| 周 | 事项 | 产出 |

# 第二部分：检索评估扩样本

## B1. 现状与问题

- 数据集：`corpus/eval/teacher_questions.json`，15 条真人问题，五类（主题词/题型+知识点/教材概念/年份+卷别/自然语言），`expect_verified 15/15`；原文件缺编号 11–15，未补造。
- 基线：旧引擎 Recall@8 26.7%；混合检索 **93.3%（14/15）**、MRR 0.836、空结果 0%。
- 问题：**样本太小**（14/15 的 95% CI 约 ±13pp）、判定为 lenient 片段匹配、无 strict target、类别/模块覆盖不全、同一批 15 条被反复使用易产生“对测试集调参”嫌疑。

## B2. 目标与规模

| 项 | 建议 |
| --- | --- |
| 目标规模 | **初期验收集 60 条**（README 要求 ≥20–40，60 才够分五类 × 12 并做分层）；**长期评测集 ≥100 条 strict 查询**（逐步扩，见 B10） |
| 类别配额 | 主题词 12 / 题型+知识点 12 / 教材概念 12 / 年份+卷别 12 / 自然语言 12 |
| strict target | 初期 **30 条**（≥50%）带 `expect.strict`（只给**唯一确定对象**）；长期 **≥100 条 strict**，覆盖教材定义/定理/公式/完整题目（B10）；strict 指标分母只算这些条目 |
| 证据不足专项 | 另设 **5 条“无答案/证据不足”** 查询（不并入主指标，单独报告“是否正确拒绝”） |
| 教师来源 | 2–3 位教师，各 15–20 条；不要求全部来自同一位 |
| 冻结版本 | `teacher-questions/v2`，数据集 sha256 + DB 快照计数 + git commit 一起记录 |

## B3. 采样矩阵（防只收“系统答得对”的题）

按以下维度分层，每类内尽量覆盖：

| 维度 | 取值 |
| --- | --- |
| 模块/知识点 | 12 个模块（集合/函数/导数/三角/向量/复数/立体/解析/数列/概率统计/计数原理/不等式）；每模块 ≥3 条 |
| 来源类型 | 教材块 / 高考真题 / 模拟题 各 ≥15 条 |
| 年份 | 2022–2026 近五年 ≥30 条；更早 ≥10 条 |
| 题型 | 选择/填空/解答/证明；教材概念题单列 |
| 难度/用途 | 容易/中等/压轴；课堂小测/作业/复习 |
| 是否可答 | 包含至少 5 条“语料里可能没有/不充分”的真实需求，单独标记 |
| 精确对象类型 | `definition` / `theorem` / `formula` / `question`（可选 `example` / `section`）；初期 30 strict 按 8/6/6/10 分配，长期 100 按 25/20/20/35 分配 |

采集纪律沿用现有 README §6：**逐字记录、一条一个意图、不得只收答得对的、模拟候选不得冒充真人**。

## B4. 标注与核验（比 v1 更严）

每条记录：

| 字段 | 说明 |
| --- | --- |
| `text` | 教师原话（不改写） |
| `category` | 五类之一（+ `unanswerable` 专项） |
| `intent` | 检索意图（找题/找概念/按年份/按题型） |
| `object_type` | 期望对象：`question` / `textbook_block` / `definition` |
| `expect.any` | 至少一个可判定片段（保留 v1） |
| `expect.strict` | 精确对象：**chunk_id 集合**（新增；从 DB 导出，不靠片段猜测） |
| `gold_rationale` | 为什么这些 chunk 是标准答案 |
| `expect_verified` | 两位核验人独立核验后置 true |
| `provenance` | 教师匿名 ID、教龄段、收集日期 |

核验流程：

1. 提问教师只提供问题；**核验人不参与提问**；
2. 核验人在冻结的 DB 快照上用 SQL 找 gold chunk，填 `strict` 与 `any`；
3. 第二位核验人独立复核（hit/no-hit + strict 是否正确）；
4. 分歧由第三人裁决；记录一致率，目标 **Cohen's κ ≥ 0.70**（hit/no-hit）；
5. 数据集 freeze：sha256 + 快照（sources/chunks/questions 计数）+ 版本号 `teacher-questions/v2`；
6. **冻结后不再用于调参**；调参另建 dev 集（可选 20 条，明确隔离）。

## B5. 指标与验收（新增：5 个检索指标）

### B5.1 指标总览

| 指标 | 类型 | 评测范围 | 是否作为发布门槛 |
| --- | --- | --- | --- |
| Recall@8 | 核心指标 | 全部查询 | **是（≥85%）** |
| Strict Recall@8 | 核心指标 | 带 `expect.strict` 的查询 | **是（≥70%）** |
| MRR@8 | 诊断指标 | 带 `expect.strict` 的查询 | 否 |
| Strict@1 | 诊断指标 | 带 `expect.strict` 的查询 | 否 |
| Strict-all@8 | 诊断指标 | 带 `expect.strict` 的查询 | 否 |

**第一阶段只使用两个正式发布门槛**：Recall@8 ≥85%、Strict Recall@8 ≥70%。三个诊断指标用于定位问题（排序靠后、首位不准、多 chunk 不完整），**不设额外数值门槛，也不因它们未达某比例阻止发布**；后续根据真实数据再决定是否升级为门槛。

### B5.2 Recall@8（发布门槛）

- 分母：全部可判定查询 `N`；
- 命中：top-8 内出现任一 `expect.any` 命中（lenient）；
- 门槛：**≥85%**（v2.0 初期验收集；同时报告 Wilson 95% CI）。

### B5.3 Strict Recall@8（发布门槛）

- 分母：**只算带 `expect.strict` 的查询**（如 60 条里 30 条带 strict，分母 30；不是全部 60）；
- 金标对象：数据库里的**精确对象**（`chunk_id` 集合，来自冻结快照），不是文本片段；一个题目/一条教材定义被切成多块时，gold 是该对象的 chunk 集合；
- 命中：top-8 里出现**至少一个** gold chunk，即算 strict 命中（记录首次命中位置 `strict_rank`）；
- 不算 strict：只命中同主题/相邻块、答案/解析块（除非标注时纳入 gold）、或同题非 gold chunk；
- 门槛：**≥70%**（strict 分母上；例 30 条 → ≥21 条）；
- 统计限制：30 条 strict 的 70% 点估计 95% Wilson CI 约 **52–84%**，只作初期验收信号，不作长期门禁（长期扩到 ≥100 strict 后再定门槛，见 B10）。

### B5.4 MRR@8（诊断，不作门槛）

用于衡量精确 gold chunk 的**排序位置**，评估 Embedding / 混合检索 / Reranker 是否把精确对象排得够靠前。

- 分母：带 `expect.strict` 的查询；
- 对每条查询：检查 top-8，找到第一个属于 gold 集合的结果，记录 `strict_rank`；top-8 无 gold 则该条得 0；
- 公式：`MRR@8 = (1/N) · Σ RR_i`，其中 `RR_i = 1/strict_rank_i`（`strict_rank_i ≤ 8`），未命中为 0；`N` = strict 查询数。

| 查询 | 首次 gold 位置 | RR |
| --- | ---: | ---: |
| Q1 | 1 | 1.000 |
| Q2 | 2 | 0.500 |
| Q3 | 4 | 0.250 |
| Q4 | 8 | 0.125 |
| Q5 | 未命中 | 0 |
| **示例** | — | **0.375** |

用途：比较不同 Embedding 模型、评估 Reranker 是否改善精确对象排名、发现 gold 排名靠后问题。

### B5.5 Strict@1（诊断，不作门槛）

用于衡量精确 gold chunk 是否出现在**第一**位。

- 分母：带 `expect.strict` 的查询；
- 命中：Top-1 结果属于 gold 集合（只要命中任意一个 gold chunk 即算，不要求多个 gold 全部出现）；
- 公式：`Strict@1 = Top-1 命中的 strict 查询数 / strict 查询总数`；
- 示例：30 条 strict 中 Top-1 命中 18 条 → 60%。

用途：观察首位命中能力、对比 Reranker 开启前后 Top-1、定位“gold 经常排在相似内容之后”。

### B5.6 Strict-all@8（诊断，不作门槛）

用于衡量 Top-8 是否**完整包含**该查询的全部 gold chunk（与 Strict Recall 的“至少一个”不同）。

- 分母：带 `expect.strict` 的查询；
- 命中：该查询的**全部 gold chunk** 都出现在 Top-8；缺少任意一个即未命中；
- 公式：`Strict-all@8 = Top-8 完整包含 gold 集合的 strict 查询数 / strict 查询总数`。

示例（gold = `chunk_101/102/103`）：Top-8 含 101/102/103 → 命中；只含 101/102 → 未命中（缺 103）。

用途：检查完整题目/教材内容等多 chunk 对象的召回完整性、观察切块策略是否漏内容、分析多 chunk gold 是否难以完整进 Top-8。

### B5.7 四个 strict 指标的区别

| 指标 | 核心问题 | 命中条件 |
| --- | --- | --- |
| Strict Recall@8 | 有没有找到精确对象？ | 至少一个 gold chunk 在 Top-8 |
| MRR@8 | 第一个精确对象排得靠前吗？ | 首次 gold 位置的倒数排名 |
| Strict@1 | 第一名是不是精确对象？ | Top-1 至少一个 gold chunk |
| Strict-all@8 | 所有精确对象是否完整召回？ | Top-8 包含全部 gold chunk |

注意：Strict Recall 不要求全部 gold 进 Top-8；MRR 只看首次命中位置；Strict@1 是 MRR 的首位补充；Strict-all@8 要求完整召回。

### B5.8 最终评测配置

```yaml
retrieval_evaluation:
  release_gates:
    recall_at_8:
      denominator: all_queries
      threshold: 0.85
    strict_recall_at_8:
      denominator: strict_queries_only
      threshold: 0.70
      hit_rule: at_least_one_gold_chunk_in_top_8
  diagnostic_metrics:
    mrr_at_8:
      enabled: true
      denominator: strict_queries_only
      miss_score: 0
      rank_source: strict_rank
    strict_at_1:
      enabled: true
      denominator: strict_queries_only
      hit_rule: top_1_contains_at_least_one_gold_chunk
    strict_all_at_8:
      enabled: true
      denominator: strict_queries_only
      hit_rule: top_8_contains_all_gold_chunks
  reporting:
    - total_query_count
    - strict_query_count
    - strict_hit_count
    - strict_miss_count
    - strict_rank_distribution
    - mrr_at_8
    - strict_at_1

  constraints:
    - diagnostic_metrics_do_not_block_release
    - strict_denominator_excludes_non_strict_queries
```

### B7.1 运行成本估算（当前设备，基于 2026-11-06 实测参数）

> 设备：Intel Core Ultra 5 125H / 14C18T / 31.6GB RAM / 无独显；模型已缓存（不计下载）；fp32 CPU。

| 环节 | 实测 | 60 条评测 | 100 条评测 |
| --- | --- | ---: | ---: |
| query embedding（batch 32） | 4.26 queries/s | ~14s | ~24s |
| pg_trgm + Qdrant 检索 | ~0.15s/query | ~9s | ~15s |
| Reranker（40 候选/query） | mean **82.7s**、p95 109.6s | **~83min**（p95 110min） | **~138min**（p95 183min） |

- **无 rerank 组（L/T/V/H）**：60 条约 1 分钟，100 条约 1–1.5 分钟（含模型加载）；
- **含 rerank（HR）**：60 条约 **1.4 小时**（p95 1.8h），100 条约 **2.3 小时**（p95 3.0h）；rerank 占 99% 时间；
- **全量索引重建**：12,973 chunks × ~1.5 chunks/s ≈ **2.4 小时**（12902 chunks 实测 2h24m）；**当前 Qdrant 已是 12,973 points，无需重建**；若只是增量 N 条，约 N/1.5 秒 + 模型加载（100 条约 1–2 分钟）；
- **降本选项**：rerank 候选 40→20 约 41s/query（60 条 41min、100 条 69min）；40→10 约 21s/query（60 条 21min、100 条 35min），但需重测质量后再定；
- **规划建议**：100 条 + rerank 按 **2.5–3 小时**排后台 job；不要与索引重建同时跑（CPU 争抢）；内存 embedding ~2.7GB + reranker ~2.9GB，31.6GB 足够。

### B7.2 改用 Qwen API 的耗时估算（未实测，按公开限制与典型延迟）

> **2026-11-07 决策**：embedding 用 `qwen3.7-text-embedding`，rerank 用 `qwen3.7-text-rerank`，**均走 DashScope 原生 API**；本地 Qwen3-Embedding/Reranker 只保留为离线回退。
> 依据：`qwen3.7-text-embedding` 单请求 20 条、每条 131072 token；`qwen3.7-text-rerank` 单请求最多 500 docs、单条/请求输入上限 32768 token（阿里云百炼文档）。API 延迟与 **RPM/TPM 配额、并发**强相关，以下为估算区间；执行前应先用 `backend/tests/check_qwen.py` 校准。

| 环节 | 假设 | 60 条评测 | 100 条评测 |
| --- | --- | ---: | ---: |
| query embedding（API） | v4、10 条/请求、0.2–0.5s/请求 | 6 请求 → ~1–3s | 10 请求 → ~2–5s |
| 本地检索（pg_trgm+Qdrant） | 不变 | ~9s | ~15s |
| qwen3.7-text-rerank（API） | 1 请求/query（40 docs）、0.5–2s/请求 | ~30–120s | ~50–200s |
| **合计（含 rerank）** | 串行 | **~1–2.5 分钟** | **~1.5–4 分钟** |

- 若配额 QPS 较低（如 10 QPS），100 条 rerank 主要受排队限制，总时间仍在 **5 分钟内**；若 RPM 仅 60，排队约 100s，总约 **3–5 分钟**；
- **全量索引重建（API embedding）**：12,973 chunks / 每请求 10 条 ≈ 1,298 请求；按 2.06M token、TPM 1M 估算纯推理约 2–3 分钟，加并发与限流后约 **10–25 分钟**（本地 CPU 为 ~2.4h）；
- **部分 API 方案**：若只把 embedding 换 API、rerank 仍用本地 Qwen3-Reranker-0.6B，则 60/100 条评测仍被 rerank 主导，耗时仍是 **1.4h / 2.3h**，不变；
- **成本粗估**：全量 embedding ~2.06M token、$0.07/1M ≈ **$0.15**；rerank 100 条约 60 万 token，按百炼排序单价另计（执行前查价）；
- **不可直接比较**：API 的 `qwen3.7-text-rerank` 与本地 Qwen3-Reranker-0.6B 不是同一部署，指标可能不同；必须用同一批 query 做 smoke 对齐后再切换。

**结论**：把 embedding + rerank 都切到 Qwen API，100 条评测从本地约 2.3h 压到 **约 2–5 分钟**；收益几乎全部来自 rerank API。若只切 embedding，时间不省。

**实测（2026-11-07，中国区北京）：**

| 项 | 实测 |
| --- | --- |
| 全量索引（12,973 chunks） | 649 请求、2,332,424 input tokens、**¥1.17**、**16.3 分钟**（13.47 chunks/s） |
| 15 条评测整轮 | **约 12 秒**；rerank 平均 **0.58s/query**（本地 CPU 同任务 82.7s/query） |
| 15 条指标（原始） | Recall 14/15 = 93.3%；MRR 无重排 **0.702**、API 重排 **0.714**（本地 0.836 / 0.818） |
| 15 条指标（稀有词 rescue 后） | Recall **15/15 = 100%**；MRR 无重排 **0.780**、API 重排 **0.723** |

> MRR 下降不是“找不到”，而是排序位置变化：API embedding 与本地模型排序不同，且语义 rerank 与 v1 的 lenient 片段判定错位。**Q08 的 miss 是“近五年 + 递推”过滤冲突**，已用稀有词 rescue（≤50 chunks 视为稀有、第三路权重 3.0）修复；但这是按 15 条调的策略，**v2 strict 集上需重新确认**。详见 `corpus/eval/QWEN_API_EVAL_2026-11-07.md`。

| 类型 | 含义 | 金标 |
| --- | --- | --- |

**治理规则**：

1. **版本冻结**：v2.0 只作初期验收；v2.1 单独冻结（sha256 + DB counts + commit）；两版都保留，不能覆盖；
2. **隔离调参**：评测集冻结后不调参；调参用独立 20 条 dev 集（同样真实教师问题，但不进入验收集）；
3. **扩样本节奏**：v2.1 先补到 100 strict；之后每季度或语料大版本（教材换版/新增来源）增补 ≥20 条，淘汰坏题需记录原因；
4. **对象类型覆盖检查**：每次冻结前用脚本检查四类（定义/定理/公式/题目）各自数量与模块覆盖，任一类型 <15 条不得宣称成为长期基线；
5. **报告纪律**：所有报告必须写数据集版本、sha256、DB 快照计数、git commit；v2.0 的 70% 不能与 v2.1 的 80% 混读；
6. **长期目标**：v2.1 通过后，检索层才可对外称“有统计意义的达标”；v2.0 通过只表示“可进入下一轮教师验收”。
