## 0. 本册定位

### 0.1 本册解决什么

测试矩阵最容易出的问题不是“测得不够深”，而是**“不知道哪些没测”**。手写的清单永远看起来完整——直到上线后才发现某个状态迁移从来没跑过。

本册的做法：**能机械派生的用例一律派生，然后校验覆盖完整性。**

| 来源 | 派生用例 | 数量 |
| --- | --- | --- |
| 状态机的 136 条迁移 | 每条一个合法用例 | 136 |
| 101 个状态 | 每个一个“该状态下只允许合法动作”的拒绝用例 | 101 |
| 23 个教师动作 | 每个成功 + 失败两条 | 46 |
| 64 个接口 | 每个一条契约用例 | 64 |
| 18 个错误码 | 每个一条路径用例 | 18 |
| D3 的界面验收点 | 人工设计 | 12 |
| D1 的 18 项指标 | 人工定义采集方法 | 18 |
| 数据质量与引用完整性 | 从 D1 §7 断言派生 | 24 |
| 并发与故障注入 | 人工设计 | 10 |

合计 **429 例**，其中 365 例由脚本生成。

### 0.2 本册不做什么

- 不写测试代码。
- 不定义 CI 流水线（Phase 6 建）。
- 不定义性能压测脚本（只定指标与采集口径）。

### 0.3 产物说明

`schemas/test_plan.v1.json` **由 `design/gen_test_plan.py` 生成，不要手改**。契约变更后重新生成，`design/check_test_plan.py` 会验证：

- 每条迁移恰好一个合法用例；
- 每个（聚合，状态）恰好一个拒绝用例；
- 每个教师动作既有成功也有失败用例；
- 每个接口、每个错误码都有用例；
- 用例 ID 全局唯一。

**校验器本身带自测**：注入“删一条迁移用例”“删一个状态用例”“删一个接口”“删一个错误码”四种缺口，必须全部被检出。一个永远通过的覆盖校验器没有价值。

## 1. 测试分层

```text
L1 契约测试      接口形状、错误码、幂等、ETag          ← 每 PR 必跑
L2 状态机测试    合法/非法迁移、CAS、并发               ← 每 PR 必跑
L3 数据质量测试  黄金路径 fixture 的 AST / Citation 断言 ← 每 PR 必跑
L4 端到端测试    从建任务到导出两个文件                 ← 每日 + 发布前
L5 故障注入      Lease 丢失、outcome_unknown、SSE 断线   ← 发布前必跑
L6 指标与基线    18 项指标采集                          ← 每日统计，发布前评估
```

**顺序理由**：L1–L3 便宜且能挡住绝大多数回归；L4/L5 慢且依赖环境，放在合并后与发布前。把 L4 塞进每 PR，团队会开始绕过它。

------------------------------------------------------------------------

## 2. 状态机测试规则

### 2.1 合法迁移（SM-L-*）

每个用例的判定：

```text
给定聚合处于 from 状态，且所有守卫条件满足
当  执行对应动作
则  状态变为 to，state_version 递增 1，且写入一条业务事件与 Outbox
```

**守卫条件必须真实满足**，不能 mock 掉。例如 `publish` 用例必须真的准备好新鲜的 Gate 证据，而不是把检查跳过。

### 2.2 状态拒绝（SM-N-*）

每个（聚合，状态）用例验证：**该状态下只有 `from` 包含它的动作为成功，其余全部返回 `STATE_CONFLICT`**。

判定方式不是逐条列举禁止动作，而是：取该状态的允许动作集合（从 Registry 推导），对集合外的动作抽样验证。这样即使新增了动作，也不会漏。

### 2.3 终止态

每个终止态额外验证：任何动作都返回 `STATE_CONFLICT` 或 `TERMINAL_STATE`，且**不产生任何副作用**（无事件、无 Outbox）。这一条对应 SM-R05。

## 3. 动作测试规则

每个教师动作两条用例：

| 用例 | 判定 |
| --- | --- |
| `ACT-OK-*` | 成功；返回 `status`、`state_version`、`allowed_actions`；复合命令的成员聚合全部推进 |
| `ACT-ERR-*` | 在守卫不满足时返回**该动作声明的错误码之一**，且状态不变、无副作用 |

**复合命令必须验证原子性**：`approve_plan` 的成功用例要检查 Task、Plan Version、Plan Approval 三者同时推进；失败用例要在中途注入失败，确认三者**全部回滚**。

**幂等**：同一 `Idempotency-Key` 重放返回首次结果（200），不重复产生副作用。

## 4. 接口契约测试

每个端点至少验证：

| 检查项 | 适用 |
| --- | --- |
| 路径与参数符合契约 | 全部 |
| 跨 Owner 返回 404 而非 403 | 全部 |
| 动作接口要求 `Idempotency-Key` 与 `expected_state_version` | 动作 |
| 错误响应包含 `allowed_actions` | 全部 |
| 分页返回 `next_cursor`，不接受 offset | cursor 类 |
| 草稿保存要求 `If-Match`，冲突返回 `REVISION_CONFLICT` | `PUT /drafts/{id}/revision` |
| 导出预览与下载同源（同一渲染产物的 Hash） | 导出两个端点 |

## 5. 并发与故障注入（10 例）

| ID | 场景 | 怎么造 |
| --- | --- | --- |
| CC-01 | 两个请求同时审批同一 Plan | 两个连接同时提交 approve，断言只有一个 CAS 成功 |
| CC-02 | 两个请求同时暂停同一 Execution | 同上 |
| CC-03 | 两个 Draft 同时发布 | 第二个应进入 `needs_rebase`，且不产生第二个版本 |
| CC-04 | 发布幂等键重放 | 同键重复发布，返回同一 `material_version_id` |
| CC-05 | 旧 Fencing Token 写入 | 杀 Worker 后让旧进程继续写，断言不能推进状态 |
| CC-06 | `outcome_unknown` 三种对账 | 人工造三种结果，验证不重复调用有副作用的工具 |
| CC-07 | SSE 断线回放 | 断连 30 秒后带 `Last-Event-ID` 重连，投影与数据库一致 |
| CC-08 | Chat 基线 Revision 不一致 | 提交修改时草稿指针已变，断言返回冲突且未修改 |
| CC-09 | 检查期间修改 Draft | 旧报告变 `stale`，发布门禁拒绝 |
| CC-10 | 发布事务逐步失败 | 在 15 步中逐个注入失败，断言无孤立版本、无重复消费审批 |

**CC-10 是最贵但最值钱的一条**：发布是唯一会产生不可回收副作用的操作（不可变版本 + 审批消费），它必须被证明“失败即回滚”。

## 6. 界面验收（12 条）

按 D3 §6 逐条验收，全部为**可自动化或可断言**的检查，不依赖主观评价：

| ID | 断言方式 |
| --- | --- |
| UI-01 | 遍历每个页面，统计 `primary` 按钮数量 ≤ 1 |
| UI-02 | 构造 `allowed_actions` 为空的响应，断言按钮区为空（不是灰按钮） |
| UI-03 | 对每个数据区块注入加载/空/错/冲突四种状态，断言都有对应呈现 |
| UI-04 | 提交过期 ETag，断言出现对比面板且无静默覆盖 |
| UI-05 | 切到学生视图，断言答案节点不在 DOM 中（而非 `display:none`） |
| UI-06 | 点击问题条目，断言证据展开且跳转到对应节点 |
| UI-07 | 忽略 S1 时不填理由，断言提交被阻止 |
| UI-08 | 让 Gate 过期，断言发布按钮禁用并给出重新检查入口 |
| UI-09 | 发布成功后断言提示包含版本号与“不可修改” |
| UI-10 | 断言预览 URL 与下载 URL 指向同一产物 Hash |
| UI-11 | 断开网络 30 秒再恢复，断言界面状态与接口一致 |
| UI-12 | 造 `outcome_unknown`，断言按钮置灰且出现“不要重复提交”提示 |

**UI-05 必须查 DOM 而不是截图**：这是“投影”与“隐藏”的唯一可判定差别。

## 7. 指标采集口径（18 项）

| 指标 | 采集方式 | 阻断 |
| --- | --- | --- |
| M1–M3 可追溯性 | 黄金路径 fixture 自动断言 | 是 |
| M4–M6 数学质量 | Validator 结果聚合 + 固定数据集 | M4/M5 是，M6 观察 |
| M7–M12 效率与教师成本 | 埋点：Task/Plan/Execution/Draft 的时间戳与编辑计数 | 观察 |
| M13–M14 导出安全 | 导出产物自动断言（学生版节点计数） | 是 |

**M7–M12 需要真实使用数据**，Phase 6 前只能取到测试环境数据，不作为发布依据，仅用于发现异常（如 P95 远超预期说明有性能问题）。

| 项 | 要求 |

| 数据库 | PostgreSQL 17，独立实例，每轮用例前重建 |

## 附录 B：覆盖完整性怎么保证

```text
契约变更
   ↓
python design/gen_test_plan.py        重新生成 429 例
   ↓
python design/check_test_plan.py      校验覆盖缺口
   ↓
缺口非空 → 构建失败
```

关键点：**测试矩阵不是文档，是构建产物。** 它和契约一起版本化，契约变了它自动变，人不需要记得更新。

这样“没测”和“测过了”就有了可判定的区别——这是本册唯一的目的。
