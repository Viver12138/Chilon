## 0. 本册定位

### 0.1 本册解决什么

D2 定了有哪 13 个页面、每页调哪些接口；本册定**页面上放什么、什么时候放、出错时怎么办**。

| 问题 | 本册回答 |
| --- | --- |
| 三栏怎么排、小屏怎么退 | §1.1 |
| 通用状态（加载/空/错/冲突）怎么表现 | §1.3 |
| 每个黄金路径页有哪些区块、什么顺序 | §2 |
| 按钮什么时候出现、什么时候禁用 | §1.4 |
| 实时更新断线了怎么办 | §1.5 |
| 骨架页面要不要详细设计 | §3（简版即可） |
| 跨页流程怎么串 | §4 |

### 0.2 本册不做什么

- 不定义视觉稿、色彩、字体、组件库（后续 Design System）。
- 不定义移动端布局（第二批）。
- 不定义 Admin、知识审核队列、账户设置（`deferred` 页面）。
- 不重复 D4 的文案——只引用。

### 0.3 走查结论与未验证清单

2026-11-04 完成 1 位教师（高三、教龄 3 年）的场景 A 走查。

| 假设 | 状态 | 依据 |
| --- | --- | --- |
| 计划审批页可理解 | ✅ 已验证 | 教师能主动说出在批准什么 |
| 七道门禁负荷可接受 | ⚠️ 弱验证 | 无“想跳过”反馈；样本仅 1 人且教龄偏短 |
| 术语（项目/材料/草稿）合适 | ✅ 已验证 | 教师用语一致 |
| S0–S3 分级可被理解 | ⚠️ 部分验证 | 教师主动点开了证据 |
| 学生版可被信任 | ❌ **已证伪** | 教师：“我得自己下载看一下” → 改为预览方案（§2.5） |

**未覆盖、仍属假设的部分**：

1. **场景 B（改讲义）未验证**——D1-03「教师编辑不重审 Plan」仍只有推理支撑。
2. **场景 C（课堂小测）未验证**——G3 自动批准是否可接受未知。
3. **场景 D（纸质资料）未验证**——知识库上传的产品价值未验证。
4. 教龄 3 年的样本可能高估了对流程化工具的容忍度。

**本册据此的原则**：涉及未验证场景的页面（`export_center`、知识库相关），把交互做得**可收敛**——先用最保守的形态上线，等验证后再放宽，而不是一次做到最简。

## 1. 全局框架

### 1.1 三栏布局与断点

| 断点 | 布局 | 说明 |
| --- | --- | --- |
| ≥ 1440px | 左导航 240 + 主区自适应 + 右栏 360 | 桌面标准 |
| 1280–1440px | 左导航 200 + 主区 + 右栏 320 | 主区仍可读 |
| 1024–1280px | 左导航收窄为图标 64 + 主区 + 右栏抽屉 | 右栏点按唤出 |
| < 1024px | 单栏 + 底部标签栏 | 仅支持查看与审批，不承诺编辑体验 |

**右栏内容按页面而定**：

| 页面 | 右栏放什么 |
| --- | --- |
| `task_detail` | 计划摘要、允许动作 |
| `draft_editor` | AI 对话 |
| `quality_report` | 问题列表（可筛选严重度） |
| `publish_review` | 门禁快照与来源权利 |
| `export_center` | 导出记录 |

**硬规则**：右栏不是“次要信息堆放区”，它必须是当前页面的**第二决策面**。若某页右栏没有决策价值，就不设右栏，主区占满。

### 1.2 导航与路由守卫

按 D2 §2/§7 执行：

- 未登录 → 跳登录，保留 `return_to`。
- 跨 Owner 或不存在 → `404`，不区分“没权限”和“不存在”。
- `deferred` 页面在 MVP 不注册路由，直接 404。
- 路由切换不做整页刷新；数据走接口，状态只认接口返回。

### 1.3 页面通用状态

每个数据区块必须实现四种状态，缺一不可：

| 状态 | 表现 | 约束 |
| --- | --- | --- |
| 加载中 | 骨架屏，保留布局高度 | 不用整页 loading 遮罩 |
| 空 | 一句说明 + 一个可点的出口 | 不允许只有文字提示（D2 §8） |
| 错误 | 错误码 + 中文说明 + `allowed_actions` 里的可恢复动作 | 见 §1.4 |
| 冲突 | 显式对比面板 | 见 §1.3.1 |

#### 1.3.1 冲突处理面板

草稿保存冲突（`409 REVISION_CONFLICT`）时，不允许静默覆盖，也不允许自动合并。展示三选一：

| 选项 | 行为 |
| --- | --- |
| 查看差异 | 并排展示我的版本与最新版本，仅文本级 diff，不做三方合并 |
| 用最新覆盖我的 | 丢弃本地未保存修改，需要二次确认 |
| 保留我的，另存为副本 | 创建新 Draft，`change_origin = teacher_edit` |

**结构性冲突**（节点增删、来源变更）不提供“自动重放”，只能人工处理。

#### 1.3.2 超时与结果未知

任何动作请求超时，**不得直接提示“失败”**。按 SM-R09：

```text
超时 → 提示"正在确认结果"
     → 轮询对应聚合（GET 该资源）
     → 状态已推进 → 按成功处理
     → 仍未推进且超过阈值 → 提示"结果未确定，可稍后刷新"
```

`outcome_unknown` 状态下按钮置灰，并提示“不要重复提交”。

### 1.4 allowed_actions 驱动按钮

**前端不自行判断按钮可用性。** 每个页面渲染动作区时，只读响应里的 `allowed_actions`，与 D4 的动作标签做映射。

| 规则 | 说明 |
| --- | --- |
| 按钮出现 | 动作在 `allowed_actions` 中 |
| 按钮禁用 | 接口返回了动作但带阻塞原因（`blocked_reasons`）时，禁用并显示原因 |
| 按钮缺席 | 不在 `allowed_actions` 中；不显示灰按钮，避免制造“为什么不能点”的疑问 |
| 主按钮 | 每屏最多一个 `ui = primary` 的动作 |
| 危险动作 | `ui = danger`，必须二次确认，确认文案写明后果 |

**为什么不在前端判断**：D4 的动作表与 D2 的门禁策略是唯一权威。前端再写一份状态判断，必然与后端漂移。

### 1.5 实时更新

| 场景 | 机制 |
| --- | --- |
| 执行进度 | SSE `execution.progress` |
| 检查完成 | SSE `activity.updated` 或轮询 `GET /quality-runs/{id}` |
| 断线 | 按 `Last-Event-ID` 重连回放（D5 §6.3） |
| 兜底 | 页面可见时每 30 秒 `GET /activity` 对账；不可见时暂停 |

**原则**：SSE 只让界面“看起来最新”，事实来源永远是接口返回的聚合状态。断线期间的界面不得显示为“成功”。

## 2. 黄金路径页面

统一模板：**目的 / 进入条件 / 布局 / 读接口 / 动作 / 状态处理 / 交互规则 / 关键文案**。

### 2.1 `task_detail` 任务详情与计划审批

**目的**：让教师在生成前确认“要用哪些资料、生成什么、做什么检查”，然后批准或要求修改。

**进入条件**：从项目概览的任务列表进入；Task 处于 `draft` 至 `running` 任一状态。

**布局**（主区三块，纵向）：

| 区块 | 内容 | 出现条件 |
| --- | --- | --- |
| A 要求摘要 | 年级、专题、内容类型、题量、题源构成 | 始终 |
| B 执行计划 | 将使用的资料、讲义结构、题量与来源分布、将执行的检查、预计耗时 | `planning` 之后 |
| C 执行进度 | 步骤进度、当前动作、已用时长 | `running` 至终态 |

右栏：计划版本号与批准状态、允许动作列表。

**读接口**：`GET /tasks/{id}`、`GET /tasks/{id}/plan`、`GET /executions/{id}`

**动作**（按 `allowed_actions`）：

| 状态 | 出现的动作 |
| --- | --- |
| `draft` | 提交教学要求、取消任务 |
| `planning` | 取消任务 |
| `awaiting_plan_approval` | 批准执行计划（主）、要求修改计划、取消任务 |
| `ready` | 取消任务 |
| `running` | 暂停执行、请求取消任务 |
| `paused` | 继续执行、请求取消任务 |
| `needs_attention` | 重新规划、重试执行、取消任务 |

**状态处理**：

| 状态 | 页面表现 |
| --- | --- |
| `draft` | 只显示 A 块 + 要求编辑表单；B 块显示“生成计划后可查看” |
| `planning` | B 块骨架屏 + “正在检索资料并生成计划” |
| `awaiting_plan_approval` | B 块展开，底部固定动作条（批准为主按钮） |
| `running` | C 块替换 B 块的显眼位置，B 折叠为摘要 |
| `needs_attention` | 顶部警示条 + 失败原因 + `capability_gap` 时展示三选一决策卡 |

**`capability_gap` 决策卡**（D1 §5.3）：

```text
资料不足：需要 10 道高考真题，当前可用 7 道。

[补充资料]  [降级接受]  [修改要求]

降级接受 → 说明后果：3 道将改为 AI 自编题，单独成组并标注来源
```

**交互规则**：

1. 计划块里的每份资料可点开看来源详情（书名/年份/页码）。
2. 批准是**单次**动作，点击后按钮立即置灰并显示“正在批准”，防重复提交。
3. 要求修改必须填写意见（不能空提交），意见进入下一轮计划。
4. 生成中允许离开页面，回来时按接口状态恢复，不依赖本地状态。

**关键文案**：见 D4 §6 的 Task 状态表；`capability_gap` 文案见上。

### 2.2 `draft_editor` 材料编辑与 AI 对话

**目的**：教师在这里读、改、让 AI 改同一份文档。

**进入条件**：Material 有 `current_draft`，或从 `task_detail` 的交付物跳转。

**布局**：

| 区域 | 内容 |
| --- | --- |
| 主区左 | 结构化文档大纲（章节树，可折叠） |
| 主区中 | 文档正文，块级编辑 |
| 右栏 | AI 对话（消息流 + 输入框 + 引用附件） |
| 顶部条 | 草稿状态、Revision 号、保存状态、动作区 |

**读接口**：`GET /materials/{id}`、`GET /drafts/{id}`（拿 ETag）、`GET /drafts/{id}/revisions`、`GET /conversations/{id}/messages`

**写接口**：`PUT /drafts/{id}/revision`（带 `If-Match`）、`POST /conversations/{id}/messages`

**动作**：提交检查（主）、中止检查、放弃草稿、恢复编辑

**状态处理**：

| 草稿状态 | 编辑行为 |
| --- | --- |
| `editing` | 正常编辑，自动保存 |
| `checking` | 允许编辑；首次编辑立即提示“修改会让当前检查失效，检查会重新开始” |
| `changes_required` | 可编辑；顶部显示问题数与“去查看问题”链接 |
| `awaiting_review` | 可编辑；编辑后自动回到 `editing` 并提示审批作废 |
| `approved` | 只读，顶部提示“已批准，如需修改请先撤回批准” |
| `needs_rebase` | 只读，提示需先合并；显示合并入口 |
| `published` | 只读，提示“正式版本不可修改，可基于它新建草稿” |

**自动保存规则**（D1 §4.2）：

- 内容变化 + 距上次保存 ≥ 2 秒才发请求。
- 保存中顶部显示“保存中”，成功显示“已保存 · 14:32”，失败显示“保存失败，点击重试”。
- 冲突一律走 §1.3.1 面板，不自动重试。
- 自动保存不改变草稿状态。

**AI 对话规则**：

- 发送时记录 `base_revision_no`；回复若是修改提案，且期间草稿指针已变，则**不自动应用**，而是展示为待审 Patch（D1 §D1-04）。
- 提案卡片提供“应用 / 放弃 / 让我看看差异”。
- 对话里不允许直接触发 E2 级操作；命中时提示“这个改动需要重新规划”，并提供新建任务入口。

**块的编辑约束**：

| 块类型 | 编辑形态 |
| --- | --- |
| 段落 / 列表 / 表格 | 富文本内联编辑 |
| 公式 | LaTeX 源码 + 实时预览（D1 §D1-06） |
| 题目 | 结构化表单：题干、选项、答案、解析分区 |
| 图片 | 上传替换，强制填 alt |

**可见性**：教师版可见答案与解析；切换到“学生视图”时从 AST 投影，**不是前端隐藏**。

### 2.3 `quality_report` 质量报告与数学验证

**目的**：让教师看懂“哪里可能有问题、证据是什么、要不要处理”。

**进入条件**：Draft 有至少一次检查 Run。

**布局**：

| 区块 | 内容 |
| --- | --- |
| A 结论条 | Gate 结果（`passed` / `passed_with_warnings` / `blocked` / `inconclusive`）+ 阻断数 |
| B 问题列表 | 按严重度分组；每条含位置、描述、证据入口、处理动作 |
| C 通过项摘要 | 通过了多少项检查，可展开 |
| D 数学验证 | 公式/答案的验证结果，`unsupported` 与 `inconclusive` 单独列出 |

右栏：筛选器（严重度、类型）、“只看阻断项”开关。

**严重度呈现**：

| 级别 | 颜色语义 | 是否阻断 | 教师可否忽略 |
| --- | --- | --- | --- |
| S0 | 红 | 是 | **不可** |
| S1 | 橙 | 是（默认） | 可，但必须填写理由并二次确认 |
| S2 | 黄 | 否 | 可 |
| S3 | 灰 | 否 | 可 |

**交互规则**：

1. **证据必须可展开**。每条问题点开后显示：节点位置、原文片段、规则名与版本、Validator 输出。
2. 点击问题跳到 `draft_editor` 对应节点并高亮。
3. `inconclusive` / `unsupported` 不能显示为“通过”，必须单列。
4. 忽略 S1 的流程：点“忽略” → 弹窗要求填写理由 → 记录到 `quality_issue_feedback` → 按钮变为“已接受风险”。
5. 检查运行中显示“中止检查”，不显示结果。

**关键文案**：

- `passed_with_warnings`：「可以通过。有 N 个警告，不影响发布。」
- `blocked`：「有 N 个问题必须处理。」（不写“失败”，避免教师以为程序坏了）
- 技术失败：「检查程序执行失败，这不是内容问题。」（D4 §6 已定）

### 2.4 `publish_review` 发布审核

**目的**：让教师做一次性的、有证据支撑的发布决定。

**进入条件**：Draft 处于 `awaiting_review`。

**布局**：

| 区块 | 内容 |
| --- | --- |
| A 变更摘要 | 相对 base 版本改了什么（节点级统计，不是 diff 文本） |
| B 门禁快照 | 质量结论 + 数学验证结论 + 检查运行时间 + 是否新鲜 |
| C 来源与权利 | 引用了哪些来源、各自权利状态、是否有 Attribution 要求 |
| D 学生版剔除摘要 | 将剔除多少答案/解析/教师备注节点，附预览入口 |
| E 发布影响 | 将生成正式版本号、是否不可修改 |

动作条：发布（主）、要求修改、撤回发布批准。

**交互规则**：

1. **发布前必须能预览学生版**（§2.5），不在本页内嵌，提供跳转。
2. 门禁快照过期时，发布按钮置灰，提示“检查已过期，请重新检查”，并给出跳转。
3. 来源权利未确认时，列出具体哪几份来源需要确认，给“去确认”入口。
4. 发布是一次性动作：点击后锁定按钮，成功跳转到导出或版本页。
5. 发布成功提示必须明确“已生成不可修改的正式版本 vN”。

### 2.5 `export_center` 导出中心

**目的**：让教师拿到可直接用的文件，并且**能自己验证它是对的**。

**进入条件**：Material 有已发布版本。

**布局**：

| 区块 | 内容 |
| --- | --- |
| A 版本选择 | 当前版本与历史版本 |
| B 导出类型 | 教师版 / 学生版，各自说明包含与排除什么 |
| C 预览 | 渲染后文件的浏览器内预览（分页/滚动） |
| D 导出记录 | 历史记录：类型、时间、状态、有效期、下载 |

**两步骤流程**（D.19）：

```text
选类型 → 请求导出 → 状态 queued/rendering/uploading
                   → ready：显示「预览」与「下载」
                   → 预览 = 同一份渲染产物在浏览器内打开
                   → 教师翻看后点下载
```

**为什么不再用“已核对 0 个”**：走查中教师明确表示“我得自己下载看一下”。系统声明不能替代可验证性。剔除数量仍显示，但只作为辅助信息，不作为可信性依据。

**交互规则**：

1. `ready` 前不显示下载按钮，显示进度。
2. 预览与下载同源；预览地址有效期 10 分钟，过期可重新申请。
3. 过期（`expired`）后提示“文件已过期，请重新导出”，提供一键重导。
4. 学生版导出的预览默认打开，教师版不强制。
5. 下载不暴露 `storage_key`，一律走短时效 URL。

**未验证提示**：学生版信任问题已被证伪，预览方案本身也**待验证**。上线后要专门确认：教师看到预览后是否还会下载自查。

## 3. 骨架页面（简版）

| 页面 | 必要内容 | 约束 |
| --- | --- | --- |
| `home` | 最近项目、最近材料、待处理任务（`needs_attention`、`awaiting_plan_approval`） | 空状态给出“创建第一个项目”与“上传资料”两个出口 |
| `project_list` | 项目卡片（名称、材料数、最近更新） | 一句“项目 = 一个教学专题” |
| `project_overview` | 项目信息、任务列表、材料列表 | 任务与材料分两块，不混排 |
| `material_list` | 区分项目材料与个人材料 | 个人材料标注“不隶属于项目” |
| `version_viewer` | 只读渲染 + 版本元信息 + 引用来源列表 | 不提供任何编辑入口；提供“基于此版本新建草稿” |

骨架页面不做右栏，不为它们设计复杂交互。

## 4. 跨页流程串联

```text
项目概览
  └─ 新建任务 → task_detail（填要求）
        └─ 计划生成 → task_detail（审批）──批准──┐
                                                 ↓
                                          生成中（同页）
                                                 ↓
                                          交付 Draft
                                                 ↓
                        draft_editor（编辑 / Chat）→ 提交检查
                                                 ↓
                        quality_report（看问题）→ 处理 → 重新检查
                                                 ↓
                        publish_review（批准）→ 发布
                                                 ↓
                        export_center（预览 → 下载）
```

**三个必须保持一致的衔接点**：

1. `task_detail` 批准后，页面不跳转，原地显示执行进度。
2. `quality_report` 点击问题跳回编辑器并定位节点，返回时保留筛选状态。
3. `publish_review` 的发布成功后，直接提供“去导出”，不要求教师自己找。

## 5. 文案与可用性规则

1. **按钮文案用动词短语**：`提交检查`、`批准并发布`、`另存为副本`；不用“确定/取消”。
2. **不暴露内部标识**：界面不出现状态枚举名（如 `changes_required`）、错误码、门禁编号。
3. **错误信息三段式**：发生了什么 → 为什么 → 你能做什么。
4. **危险动作写后果**：`放弃草稿` 的确认文案必须说明修改不再可用。
5. **禁止自证式文案**：不写“系统已核对”“保证正确”。要让人能看、能查（§2.5 的教训）。
6. **数字要有单位与口径**：`6 个答案节点`、`3 道题来源不足`，不写裸数字。
